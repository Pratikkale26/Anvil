# M6.2 sunset — what's actually blocking

Per `docs/plan-pure-ast-emitter.md` Session 10, M6.2 is "delete the
legacy regex post-process layer (~3500 LoC)". That's gated on the
visitor being structurally complete — i.e., the visitor doesn't
depend on any handler / walker / regex code that M6.2 wants to delete.

This report enumerates what's left.

## Blocker #1: `visitPassThrough` → `handlePassThrough`

`visitPassThrough` (in `ast-visitor/visitor-base.ts`) captures the
output of `handlePassThrough` (in `body-emitter/handlers/pass-through.ts`)
and runs the captured text through `convertPassThroughLine` /
`tryStructuralizeMultiLine` for structural recognition. This is the
M5c approach — the visitor is byte-equal to the regex layer because
it RE-USES the regex layer's output.

Until M5d-proper replaces the regex transforms in `handlePassThrough`
with structural Rust-AST passes, the visitor remains dependent. Per
plan: **15-20hr** of focused work. Specific transforms still done by
the regex layer:

  - `replaceBumpRefs` — 4 ctx.bumps shapes (already structural in
    visitor's state ports, but pass_through still calls regex)
  - `transformCtxAccountsReferences` — ctx.accounts.X → AccountInfo
    binding lookup
  - `transformAccountReferences` — Account<T> wrapper resolution
  - `transformHelperCalls` — helper-fn rewriting
  - `normalizeKeyValueUsages` — .key()/.key normalization per target
  - `transformNestedAnchorCode` — Anchor-only macros inside expressions
  - `simplifyPassThroughCode` — CpiContext::new strip + similar
  - `normalizeToAccountInfoCalls` — .to_account_info() drop
  - sysvar qualification — Clock::get → pinocchio::sysvars::Clock::get
  - CpiContext::new cleanup — fold into invoke()
  - module::cpi::function pattern rewriter

Without these, plain pass_through code wouldn't transform correctly.

## Blocker #2: 4 Token-2022 branches still wrap legacy

`visitCpiSplMintTo` / `visitCpiSplBurn` / `visitCpiSplCloseAccount` /
`visitCpiSplSetAuthority` route to `runHandlerCapture` when
`stmt.tokenProgram === "token_2022"`. The Token-classic branch is
already structural (mlCall + invoke).

Pattern follows `visitT22Transfer` (commit `2ae5ed5`) — call the
emitter's `emitSplX(...)` to get the hand-rolled byte-array CPI block,
then parse via `parseT22PinocchioBlock`. Each port: ~30-60 min plus
parity verification on real T22 fixtures. Total: 2-4 hr.

**This commit ports 2 of 6** — `visitCpiMplCreateMetadataV3` +
`visitCpiMplCreateMasterEditionV3` (both via the new `captureAndConvert`
helper that mirrors `visitPassThrough`'s lossless conversion). Both
emit commented-out TODO stubs anyway, so the structural conversion
is mostly comment + scaffold stmt recognition. Metric unchanged at
287 (Metaplex CPIs aren't in the demo corpus).

## Blocker #3: `runHandlerCapture` infrastructure itself

Even if all 6 explicit `runHandlerCapture` call sites get ported,
the `runHandlerCapture` method in `AstVisitorBase` is the LOAD-BEARING
fallback for any future kind that hasn't been structurally ported.
Removing it means committing to "every IR kind is structural in the
visitor, no fallback." That's a hard constraint to maintain over time
as new IR kinds get added.

Recommendation: keep `runHandlerCapture` even after M6.2; it's a
small amount of code (~30 LoC) and provides a safety hatch. The
~3500 LoC M6.2 wants to delete is the per-target string-builder
emitters + handler functions, NOT the visitor's own machinery.

## What this commit ships

- `captureAndConvert` helper — same lossless tree-sitter routing as
  `visitPassThrough`, available to any visit method that wants to
  port off `runHandlerCapture` later
- 2 Metaplex visit methods migrated to the new helper (visible
  reduction of `runHandlerCapture` direct calls: 6 → 4)
